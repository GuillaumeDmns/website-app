# CLAUDE.md

Flutter mobility app for Île-de-France public transport, Citymapper-like: nearby real-time departures, search, stops, lines, journeys, favorites, traffic info. It must work on Android (main target), iOS, web and desktop (Linux, macOS, Windows). Rewritten from scratch in 2026 (the previous prototype is in git history, branch `temp`).

## Commands

```bash
flutter pub get
dart run build_runner build      # freezed / json_serializable (generated *.freezed.dart / *.g.dart are not committed)
flutter analyze
flutter test                     # unit, widget and full-app tests (fake backend), about 10 s
flutter test integration_test/app_test.dart -d linux   # the real Linux app, one file per run (opens a window; the CI uses a virtual screen)
flutter run -d <device>          # dev app on http://localhost:8080 (Android: adb reverse tcp:8080 tcp:8080 first)
tool/build.sh apk --flavor prod  # production, versioned from git (web: --dart-define=APP_ENV=prod; linux: both)
```

- **Version**: git's last tag `vX.Y.Z` is the only one (`pubspec.yaml` stays at `0.0.0`). `tool/version.sh` gives the name (`0.4.0` on the tag, `0.4.0-12` 12 commits after it), the build number (Android versionCode: `(X*10000 + Y*100 + Z)*100` + the commits after the tag, at most 99, so a later build always installs over an earlier one; minor and patch up to 99) and the commit (`-dirty` with uncommitted changes); `tool/build.sh <flutter build args>` passes them to `flutter build` (`--build-name`, `--build-number`) and to the app (`APP_VERSION`, `APP_BUILD`, `APP_COMMIT` dart-defines, `AppConfig.version`…), shown with the environment, backend (and its release, `/api/health`, `serverVersionProvider`) and platform under "À propos" (copy button, for bug reports). A plain `flutter run` / `flutter build` is a "development build" 0.0.0. Release: tag master `vX.Y.Z` and push the tag.

- **Environments** (`core/config.dart`, `AppConfig`): `prod` talks to `https://guillaumedamiens.com` only, `dev` to `http://localhost:8080` only (the backend of the development machine; Android devices and emulators through `adb reverse`); they never mix. The environment comes from `--dart-define=APP_ENV`, else on the web from the page's host (`app.guillaumedamiens.com` = prod), else from the Android flavor (`appFlavor`), else dev. Android flavors (`android/app/build.gradle`): `dev` = `com.guillaumedamiens.app.dev` "Guillaume Dev" (orange icon in `src/dev/res`, cleartext HTTP to localhost allowed by `src/dev/res/xml/network_security_config.xml`), `prod` = `com.guillaumedamiens.app` "Guillaume" (App Links in `src/prod/AndroidManifest.xml`); `default-flavor: dev` in `pubspec.yaml`, so a plain `flutter run` / `flutter build` is dev (it also reaches the Linux build folder name; iOS/macOS will need `dev`/`prod` Xcode schemes). Dev builds show a "DEV" banner and prefix the keys they store (`AppConfig.storagePrefix`: `LocalStore`, `TokenStore`, onboarding flag). `API_BASE_URL` / `WEB_APP_URL` still force the URLs.
- The home screen widget's class is addressed by its qualified name (`com.guillaumedamiens.app.NextDepartures`): the dev flavor's application id differs from the Kotlin package.
- The router keeps the requested page in `from` through the splash, welcome and sign-in pages, so deep links survive them; a signed-in user leaves the sign-in pages for `from` (`Routes.signIn(from)`).
- `--route` is ignored on Linux desktop; on the web the routes are real URLs (`/stops/IDFM:71264`, `/lines/C01743`).

## Architecture (`lib/`)

- `main.dart`: path URL strategy, `ProviderScope`. `app/`: `app.dart` (`MaterialApp.router`, locale from `localeProvider`, light/dark from the system), `theme.dart` (`AppTheme`), `routes.dart` (paths), `router.dart` (go_router: session redirect via `refreshListenable`, `ShellRoute` for the map pages), `shell.dart` (`AppShell`).
- **Layout**: `AppShell` puts the page in a side panel next to the map from 840 px wide, in a `DraggableScrollableSheet` over the map below. Pages use `PanelScrollScope.of(context)` as the controller of their main scroll view (null in the wide layout, and for pages not on top). The sheet's sizes come from the page (`_SheetProfile` in `shell.dart`): lowest height keeping the page's header, middle size (where it opens and snaps; GO fits it to the card shown with `PanelSheetScope.fitContent`), never under the status bar; search and traffic are locked at full height. Pages are laid out at least 180 px high and clipped when the sheet is lower (no overflow). Shortcuts: `/` search, `Esc` back.
- **Map** (`core/map/`): one `MainMap` behind every page, drawn by `MapLibreMainMap` on Android, iOS and the web (package `maplibre`: native SDKs, maplibre-gl-js on the web, loaded by `web/index.html` from unpkg, pinned, with a patch: the map resized with its container, `fitBounds` without the padding of the previous move; OpenFreeMap vector tiles, no key: Liberty, in dark mode too (Fiord, the dark style, showed too little); paths are style layers with a casing, pins and the user Flutter widgets over the map) and by `FlutterMainMap` elsewhere (desktop, and tests: `mapTilesEnabledProvider` false; flutter_map, Plan IGN raster tiles from the Géoplateforme, light in dark mode too); `useMapLibreProvider` chooses. A page shows things on it by wrapping its content in `MapOverlayScope(overlay: MapOverlay(pins, paths, fit))`; overlays are keyed by route location, the map shows the current one (`routerLocationProvider`). The camera only moves when `fit` changes, and frames it in the part not hidden by the panel; with `follow` (`MapFollow`: GO on foot or by bike, `goFollow`) it follows the user instead, the user at 72 % of the visible height, zoom 18, until the user moves the map ("Recentrer" button): turned by the device's heading where it has a compass (`MapFollow.compass`, `core/location/device_heading.dart`: Android's rotation vector sensor through `DeviceHeading.kt` and the `com.guillaumedamiens.app/heading` event channel, the browser's `deviceorientationabsolute` events; only listened to while following, 50 headings a second, smoothed; `FollowHeading` passes them on at most every 20 ms), else the way ahead up (`GoStep.headingFrom`: the path 30 m further than the user's projection on it); markers stay upright (the user dot turned by the heading less the map's bearing). GO asks a fix a second (Android) and starts from the last known position (`Geolocator.getLastKnownPosition`, else the app's regular one) so that the map follows at once; what the map shows (dot and camera) is `preciseUserPositionProvider`, smoothed by `GoSmoother` (`features/go/go_smoother.dart`: a glide of 0.9 s to each fix, then on along the walking or cycling way at the measured speed, 12 m at most beyond the fix), redrawn every 100 ms only while it moves and the app is in the foreground; small steps of the camera (`MapFollow.closeTo`: the smoothed position, the compass) glide frame by frame towards the last view asked (`MapFollow.glideTo`, a ticker of `MapLibreMainMap` running only until it is there, at most 60 frames a second), bigger ones are animated. The fixes themselves drive `GoTracker`. Development builds show under GO's header how the fixes come (`goFixStatsProvider`: accuracy, mean time between fixes, age). Long press (right click on desktop) on the map: `features/map_place/map_place_sheet.dart` (`MainMap.onLongPress`, given by the shell), the point named after its address (`/api/v2/places/reverse`, "Point sur la carte" without one) with "Y aller", "Partir d'ici" and the departures around.
- **API** (`core/api/`): `models.dart` (freezed models of `/api/v2` and auth), `MobilityApi` (v2 endpoints), `AuthApi`, `api_providers.dart` (every request carries `X-App-Platform` and `X-App-Version`, `AppConfig.clientHeaders`: the backend counts the devices per platform and version, anonymously). `AuthInterceptor` (dio `QueuedInterceptor`) adds the access token: the account's, renewed with the refresh token (rotated on each use, so requests wait for a single refresh), else the device's guest token (`POST /api/auth/guest`, fetched when missing or rejected); a rejected refresh token is reported to `AuthController` and the request goes on as a guest. Errors become `ApiException` (message in the app's language, backend problem detail `code`; `signInHelps` for the guest limits `guest_journey_limit` / `guest_quota_exhausted`, where `ErrorMessage` offers to sign in).
- **Auth** (`features/auth/`): `AuthController` (`unknown` / `guest` / `signedIn`). Nothing requires an account: a guest uses the whole app with capped usage (backend: a share of the PRIM quotas, a few journeys a day), favorites and recent searches on the device only; signing in (account menu, sign-in button of a guest-limit error, last welcome page, "Continuer sans compte" back) keeps them and the favorites join the account; signing out (or a lost session) clears the account's device copies and goes back to guest. `TokenStore` keeps the account's access token in memory and its refresh token in `flutter_secure_storage`, plus the device's guest token (kept at sign-out, so its daily allowance follows the device); no password exists.
- **Google sign-in** (`features/auth/google/`, packages `google_sign_in` + `google_sign_in_web`): the app gets a Google ID token and `AuthController.signInWithGoogle` exchanges it at `POST /api/auth/google`. Android: `authenticate()` opens the system account chooser (Credential Manager), `serverClientId` = the web client (`AppConfig.googleWebClientId`, so the token's audience is the client the backend accepts); Google recognises the app by package + SHA-1 through the Android OAuth clients of the project ("Guillaume Dev": `com.guillaumedamiens.app.dev` + debug key; prod: `com.guillaumedamiens.app` + upload key, and later the Play signing key). Web: Google's own button (`google_button_web.dart`, conditional import, in the app's language), results through `GoogleSignIn.authenticationEvents`; allowed origins `https://app.guillaumedamiens.com` and `http://localhost:5000` (run the dev web app on that port). Not offered on desktop and iOS yet (`googleSignInAvailable`): the login page then says so and the app goes on as a guest. Sign-in is **Google only** (no password accounts). `googleAccountChooserProvider` opens the account chooser (Android; null on the web and where Google is unavailable; the tests replace it). Sign-out and account deletion also sign out of Google.
- **Account page** (`features/auth/account_screen.dart`, `/account`, account menu when signed in; also the web URL Google Play asks for to delete an account, a guest is offered to sign in back to it): email / first name (`/api/v2/me`), export (`/api/v2/me/export`, through `exportText`: browser download, Android share sheet, else clipboard), sign-out, deletion (`AuthController.deleteAccount`: `DELETE /api/v2/me`, then the device forgets the account and carries on as a guest); for admins, `ApiTokensSection` (personal API tokens for Bruno and scripts, `/api/v2/me/api-tokens`: create with a name, value shown once with a copy button, revoke). `/api/v2/me` and its export are never served from the offline cache.
- **Location** (`core/location/`): `userLocationProvider` (geolocator, null when unavailable, e.g. Linux without GeoClue; `locationIssueProvider` + `fixLocationIssue` offer to turn location on / allow it on phones, retried when the app resumes); `nearbyOriginProvider` falls back to the map center; `nowProvider` ticks every 15 s for "3 min" labels.
- **Features** (`features/`): `home` (search box, nearby departures; `around_screen` = departures around a searched place), `search` (sends the user position, else the map center, to 3 decimals: close places first; with `?pick=<title>` it chooses a journey start/end and pops a `JourneyPlace`), `journey` (`JourneyRequest` lives in the `/journey?from=&to=&at=&arriveBy=&modes=&wheelchair=&walk=&velib=` URL; new searches get the device's `journeyPreferencesProvider` (wheelchair, walking speed, Vélib, saved from the options sheet); `velib=1` adds the backend's `bike_share` option; `from`/`to` = `here`, a stop area id or `lat,lon`; labels shared with GO and the stop pages in `journey_labels.dart` (journey type, move icon and verb, boarding, `platformLabel`); results by Navitia category (the search fixed at the top, quick chips under it: leaving in 15 / 30 min, the modes (`JourneyRequest.withMode` / `withOnly`), Vélib; each card with the next departures of its first ride, "Aussi à …", from `/lines/{id}/rides`); the detail (`journey_detail_screen.dart`, its timeline's rows in `widgets/journey_sections.dart` and `widgets/journey_timeline.dart`) keeps GO in a bar at the bottom with when to leave, shows the platform of the departure taken and the next one in case it is missed; the opened option is passed to `/journey/detail` through `selectedJourneyProvider`, lost on a web reload; `journeyOverlay` draws it on the map (walks dotted dark grey `walkPathColor`, bikes dark green `bikePathColor`, the same in dark mode since the map stays light; every path on a light casing), stops between as small dots; in the detail, "N arrêts" unfolds the stops between in the timeline (small dots on the line, times on the left, like Citymapper) and frames that ride on the map), `favorites` (`FavoritesController`: server favorites `/api/v2/me/favorites` with a device copy shown first; a guest's on the device only with negative ids, uploaded at sign-in; home/work/place shortcuts, favorite stops with live departures and lines on the home page, stars on stop and line pages, given the stop / line summary so that a guest's favorite can show it), `search/recent_searches.dart` (last 10 places/lines chosen, device only), `stops` (stop area: lines, departures, walking connections; `timetable_screen.dart` = scheduled timetable `/stops/{id}/timetable?line=&date=`, hours × minutes per direction, letters for other destinations, scrolled to the current hour), `bikes` (Vélib: stations around the home position on the map and in a section, `showBikeStationSheet`, live counts in the Vélib section of a journey detail), `lines` (directions, branches, stop timeline, path on the map, disruptions; vehicles of the direction shown from `/lines/{id}/vehicles` every minute (estimated-timetable quota), moved along their segment between fetches by `vehicleProgress` every second (`vehicleClockProvider`, only while there are vehicles), placed on the branch path with `BranchPath.place` (`VehicleMarker`: a dark pointer the way they go, a ring green on time / orange from a minute late / white without delay (`Punctuality`), faded when `stale`, i.e. missing from the latest real time; no trail; `MapLibreMainMap` keeps the layers of unchanged paths, since the package sends any new layer object to the map engine again) and on the stop timeline (`stopListPositions`: between the stop left, several stops back for a direct train, and the next one; a vehicle of another branch only once the stop it left is on the branch shown); tapping one opens `showVehicleSheet`: its next stops with times, delay, platform and mission, followed across fetches by `sameVehicle`, and "Suivre sur la carte": the map keeps it in view (`MapFollow`, north up) until stopped or gone; stops the line doesn't serve now are crossed out with "Non desservi" (`lineClosedStopsProvider`), and a stop's page fades the lines not stopping there now (`stopClosedLinesProvider`)), `traffic` (`/traffic` page: badge grid per main mode with severity dots and the disrupted lines; `TrafficSummaryCard` on the home page; `lineSeveritiesProvider` marks disrupted lines in favorites and journey results; `DisruptionList` on line/stop pages, elevator outages grouped, upcoming ones folded), `onboarding` (`/welcome` once per device after the session is known: intro, location, home/work, and for a guest what an account adds with a sign-in button; the flag is read in `main()` before `runApp` so the router redirect stays synchronous). The journey detail shows, per ride, the line's active disruptions and its departures stopping at the alighting stop from when the traveller gets to the boarding stop (`rideOptionsProvider` = `/lines/{id}/rides?after=`) in `RideDepartureList` (`journey/widgets/ride_departures.dart`, Citymapper-like: times at both stops, mission code, destination, platform; the departure taken is raised and scrolled to, unreachable ones faded). Choosing another departure retimes the journey (`journey/journey_retime.dart`, `retimeJourney`: chosen rides, else the planned departure while catchable, else the first one after the previous ride's arrival and the walk; walks follow, waits fill); GO mode uses the same list on every ride card and `GoController.choose` retimes the followed journey from that ride. Data providers are `FutureProvider.autoDispose(.family)`; real-time ones re-fetch every 30 s with a `Timer` + `ref.invalidateSelf` (Riverpod pauses them when not shown).
- **GO screen** (`features/go/`, Citymapper-like; `go_screen.dart` swipes the cards and draws the map, `widgets/` holds the header and steps' strip (`go_header.dart`), the cards (`go_move_card.dart`, `go_ride_card.dart`, `go_arrival_card.dart`) and their shared parts (`go_card_parts.dart`); `GoController` keeps a `GoState` (`go_state.dart`) and `go_live.dart` makes the system notification's content (`goLiveUpdate`) and the alerts' haptics): the map stays free, the instruction lives in the panel (kept low: GO's sheet opens at 40 % and fits its card up to 50 %; the follow camera puts the user at 72 % of the map left above it). `GoBar` floats over the map on the other pages (the current instruction, tap to open GO); on the GO page it only shows the latest alert for 20 s. The card of the step in progress tells what to do now (`goInstruction`): on foot the next turn or where to go, then pills: time to spare walking to the ride (`walkMargin`: the departure less the walk at the user's pace, `GoState.walkSpeed` averaged from the fixes; ahead / hurry / late with the next departure) and "Pas de GPS" when the schedule leads (`GoTracker.followsSchedule`); the turns folded under it ("Itinéraire détaillé"); waiting, the countdown ring. Turn by turn on foot (`go_guidance.dart`: `nextManeuver` places Navitia's `WalkStep`s along the path by their `offset`, scaled to the path drawn; within 250 m the turn is the instruction, felt 15 m ahead). The panel: arrival and "dans …", the journey's progress (`journeyFraction`), the steps' strip (tap to look at one), then one card per step: a move with its turns (folded on the step in progress), a ride with where to board (`TrainPositions`), its departures and the next one if missed, on board the stops left with their times (the map framing what is left of the ride), "Ensuite" for what comes next; a missed or cancelled vehicle offers the line's next departure in one tap (`GoIssueCard`, no new search). The arrival offers the way back and saving the trip, and closes the session after 2 min. Alerts have a kind (`GoAlert.kind`: prepare, alight, platform, urgent, info), felt apart: one Android notification channel each (`LiveJourneyNotification`, their own vibration patterns), haptic patterns in the app otherwise. Daily trip cards start GO on their next departure.
- GO platform (`platformLabel`, `goPlatformText`): "voie" for trains (`TransportMode.isRail`), "quai" otherwise, from the planned vehicle's real time; in the notification's status, the GO card (also walking to the stop), and an alert for trains when announced or changed (`platform-<step>-<platform>`).
- **Service hours** (`features/service_hours/`, GTFS only: no real-time call): `stopServiceHoursProvider` (`/stops/{id}/service-hours`) and `lineServiceHoursProvider` (`/lines/{id}/service-hours`) give today's first and last departures per direction and the frequency per period of the day (`ServicePeriod`; Flutter has its own `DayPeriod`); `serviceStatus` tells what matters now (the frequency of the current period, "Dernier départ dans …" from 60 min before the last one, the service over or not started). The stop page lists every line and direction (`StopServiceHoursSection`, a row unfolds its `FrequencyTable`), the line page the direction shown (`LineServiceHoursSummary`, matched by `ServiceDirection.direction`, counted at the stop given by `at`).
- `core/platform/live_journey.dart`: system side of GO (Android: foreground service, live notification, alerts, keep screen on through `MainActivity`; web: `browser_web.dart` = Notification and Screen Wake Lock APIs through `dart:js_interop`, conditional import with `browser_stub.dart`). Modal sheets use `useRootNavigator: true`: the pages live in the panel's navigator.
- **Sharing** (`core/platform/share.dart`): links to the web app (`AppConfig.webAppUrl`: `https://app.guillaumedamiens.com` in prod, the dev web server in dev) for stops, lines and journeys; Android share sheet through `MainActivity`, browser share sheet, else clipboard, else a dialog with the link. A journey link is `/journey/detail?<search>&dep=&lines=` (`Routes.journeyDetailOf`): `sharedJourneyProvider` runs the search again at that time and takes the option with the same lines ("Ma position" is replaced by the journey's start when sharing). Android App Links for that host (prod flavor only, `src/prod/AndroidManifest.xml`, `web/.well-known/assetlinks.json` with the signing certificate's SHA-256, served by the web app's host).
- **Daily trips** (`features/daily_trips/`): a journey option saved from its detail (bookmark button, `SaveDailyTripButton`) is kept on the device (`dailyTripsProvider`, `LocalStore` key `daily_trips`, at most 5, cleared at sign-out) with its search ("Ma position" replaced by where it starts). The home page (`DailyTripsSection`, under the shortcuts) never searches it again (no Navitia call): `upcomingTrips` retimes it with `retimeJourney` on the departures of its lines (`/lines/{id}/rides`, `watchRides`): the first departure its first ride can catch, then the next two, each with its connections. A card is named after the saved places ("Maison → Travail", `tripPlaceName` on the searched places), swaps to the way back on the same lines (`reverseJourney`; shown first in the afternoon for a trip from home), and opens the detail of its next departure. `lastTripAlert` warns an hour ahead of the last metro / train of the night from `/lines/{id}/rides/span` (`rideSpanProvider`, GTFS: first and last rides of the service day and the next day's first; lines running all night left out): the latest time to leave, else "Service terminé · reprise vers …". A ride of a journey detail taken within the half hour before its line's last one shows it (`LastRideTag`). With home and work saved but no trip between them, the home page invites to choose one.
- **Offline** (`core/offline/`): `OfflineCacheInterceptor` keeps the last 60 answers of the read endpoints (no vehicles, rides, Vélib, search) in `LocalStore` and serves them when the server can't be reached; `OfflineBanner` over the map says since when. Cleared at sign-in/sign-out.
- **Language** (`l10n/l10n.dart`): French or English, the device's choice (account menu, sign-in pages) kept in `LocalStore` and read in `main()`, else French when the system is in French and English otherwise. Changing it rebuilds the whole tree (`KeyedSubtree` in `app.dart`) so that `currentL10n` texts follow. Android resources (`values/` English, `values-fr/`) hold the native texts: notification channels, widget placeholders.
- `core/storage/local_store.dart`: small JSON documents in `SharedPreferencesAsync` (favorites copy, recent searches), cleared at sign-out so that another account never sees them (a guest's are kept at sign-in).
- `main.dart` waits (≤ 3 s) for the Inter font fetched by google_fonts: chips keep sizes measured with the fallback font otherwise.
- `core/widgets/`: `SkeletonCards` (grey pulsing cards while a list loads the first time: `AsyncView`'s default), `UpdatedAgo` (how fresh real-time data is, next to the departures' titles), `LineBadge` (IDFM look per mode), `DepartureTime` (the minutes large, "min" small, green with the real-time signal), `AsyncView`, and `ui.dart`: the shared pieces of the design (`SectionTitle`, `AppCard`, `RoundAction`, `PillTag`, `IconBubble`, `NoticeLine`).
- **Home screen widget** (Android, `features/home_widget/home_widget_sync.dart` + `NextDepartures.kt`): next departures (clock times) of the first favorite stop, else the closest one, written by `HomeWidgetSync` on the home page (at most once a minute); its refresh button runs `homeWidgetBackgroundCallback` in a background isolate (renews the access token from the stored refresh token, which the app re-reads before each renewal since the rotation revokes reused ones, or uses the guest token). `MainActivity.kt` also holds the live notification, share and keep-screen-on channel.

## Design

Citymapper-like, uncluttered: a light grey page (the sheet) with white rounded cards (`AppCard`, radius `AppTheme.radius`), near-black text, one green (`AppTheme.brand`, the color scheme's primary) for what acts or moves: real time, "Partez dans…", GO, the main action of a page (`RoundAction(primary: true)`, "Y aller"); line colors are the only other colors. State colors come from the `AppColors` theme extension (`context.colors`: `live`, `delayed`, `warning` (last metro, elevators, schedule only), `cancelled`, `card`, `muted`, `subtle`), never from `Colors.green`/`orange`. Inter has 400/500/600 only: titles are w600, nothing bolder. Pages start with a back button and a large title, then a row of round actions (stop page) or the essentials (line, journey: duration and GO), then titled sections of cards. The home page: the search pill, a suggestion in one tap (home in the evening, work in the morning, when saved and away from it), saved places as tiles (home and work tell when to leave from the daily trip saved there, `nextTripTo`, and open its next departure without a search, `goToPlace`), the traffic card, daily trips, favorite stops and lines, then the nearby departures (a long press saves a stop) filtered by kind (`NearbyFilterBar`: all, rail, bus, tram, Vélib; also filters the map pins). Dark mode mirrors it (`AppColors.dark`).

## Conventions

- State: Riverpod 3 providers written by hand (no riverpod_generator). Models: freezed + json_serializable.
- No `dart:io` / `Platform` outside platform-specific code: everything must run on the web and desktop.
- User-facing strings in `lib/l10n/app_fr.arb` (template) and `app_en.arb`, generated by gen-l10n into `lib/l10n/generated/` (not committed; `flutter pub get` or `flutter gen-l10n` rebuilds it). Widgets use `context.l10n`; code without a context (formatting helpers, `ApiException`, GO alerts and notification, home screen widget) uses `currentL10n`. Data from IDFM / Navitia (stop names, disruption messages, walking instructions) stays in French. Times from the API are UTC (`Departure.time`), display with `formatClock` / `departureLabel`.
- Stop areas (`IDFM:71264`) and IDFM line ids (`C01371`) everywhere, as in the backend v2 API.
- Accessibility: icon-only buttons get a `tooltip` (it is their screen reader label), tappable map pins a `label`. Layouts must hold with a large system text size (×1.8 checked): fixed row heights go through `MediaQuery.textScalerOf(context).scale(...)`, and crowded rows drop or move secondary items from ×1.3 (departure times, traffic badges, the stop's "Y aller" label, the journey toolbar).
- Main actions give a light haptic (GO, choosing a departure, favorites). Tests come with every change (see Tests), and the app is still checked by running it.

## Tests

- `test/support/`: `FakeBackend` (dio `HttpClientAdapter`: answers per method and path, `*` for a segment, `down` for no network, records the requests as sent), `MemoryStore` (`LocalStore` in memory), `samples.dart` (models as the backend sends them: Châtelet, Gare de Lyon, Nation, métro 1, RER A, bus 38, like the backend's integration tests), `testContainer` (providers on a fake backend; signed in when a refresh token is given), `pumpApp` (the whole `MobilityApp`, phone size, French, map tiles off, position at Châtelet, onboarding flag in memory; `settle` pumps for a while since the app keeps periodic timers; `closeApp` at the end of each test), `standardBackend()` (usual answers around Châtelet, times relative to now).
- `test/core`, `test/features`: logic (formats, geometry, models' JSON, errors, token renewal, offline cache, journey retiming, GO tracker, vehicles, session, favorites, recent searches). Code without context formats with `currentL10n`: tests set it with `useLocale` (and `initializeDateFormatting()` for dates).
- `test/flows`: the app tapped through like a user (home → stop → line → favorite, search, traffic, offline notice, language, journey and detail, guest limit, sign-in/out, account, welcome pages). Find widgets by text through `currentL10n`, by tooltip, or by type (`LineBadge`, `JourneyCard`); `visibleTexts(tester)` lists what is on screen when a test fails.
- `integration_test/`: the same harness on the real engine (`app_test.dart`, Linux desktop), and `device_heading_test.dart` (the compass of a real phone, skipped elsewhere). One file per `flutter test` run: started a second time in the same run, the Linux app never connects (the CI loops over the files).
- Seams for the tests: `dioFactoryProvider` (backend clients), `localStoreProvider`, `onboardingDoneProvider`, `localeProvider`, `userLocationProvider`, `mapTilesEnabledProvider`, `deviceHeadingProvider` (no compass in `pumpApp`), `googleAccountChooserProvider` (`pumpApp` signs in with a test ID token; pass `googleAccountChooser: null` for a device without Google); plugins without a test implementation (secure storage: `FlutterSecureStorage.setMockInitialValues`) or guarded (home widget, Google sign-in on desktop).

## CI (GitHub Actions)

- `.github/workflows/build.yml`, every pull request and push to master, two checks required to merge (branch protection): "Test" (`pub get`, `build_runner`, `flutter analyze`, `flutter test`, integration tests on the Linux app under `xvfb-run`) and "Build" (production builds through `tool/build.sh`, on the whole git history for the version: web with `--no-web-resources-cdn`, Android APK `--flavor prod`, APK kept 14 days as an artifact). Flutter pinned to the local version (3.47.6): update both together.
- `.github/workflows/deploy-web.yml`, tag `v*` (or by hand on a tag): checks that the tag is the version (`vX.Y.Z` on the commit, `tool/version.sh`), builds the production web app with `tool/build.sh`, publishes the archive in the tag's GitHub release, and the VPS downloads it as the `deploy` user (uploads from GitHub's runners to the VPS crawl at ~20 KB/s) and checks its SHA-256 (secrets `DEPLOY_HOST`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, the same as website-back's): `/var/www/guillaumedamiens-app/releases/web-<tag>-<sha>`, then the `current` link nginx serves is switched atomically; the 5 latest releases stay (roll back by pointing `current` to an older one).
