# CLAUDE.md

Flutter mobility app for Île-de-France public transport, Citymapper-like: nearby real-time departures, search, stops, lines, journeys, favorites, traffic info. It must work on Android (main target), iOS, web and desktop (Linux, macOS, Windows). Rewritten from scratch in 2026 (the previous prototype is in git history, branch `temp`).

## Commands

```bash
flutter pub get
dart run build_runner build      # freezed / json_serializable (generated *.freezed.dart / *.g.dart are not committed)
flutter analyze
flutter test                     # unit, widget and full-app tests (fake backend), about 10 s
flutter test integration_test/app_test.dart -d linux   # the real Linux app, one file per run (opens a window; the CI uses a virtual screen)
flutter run -d <device>          # dev app on http://localhost:8080 (Android: adb reverse tcp:8080 tcp:8080 first; an iPhone needs --dart-define=API_BASE_URL=http://<mac>:8080)
tool/build.sh apk --flavor prod  # production, versioned from git (web: --dart-define=APP_ENV=prod; linux: both; ios/macos: --flavor prod)
```

- **Version**: git's last tag `vX.Y.Z` is the only one (`pubspec.yaml` stays at `0.0.0`). `tool/version.sh` gives the name (`0.4.0` on the tag, `0.4.0-12` 12 commits after it), the build number (Android versionCode: `(X*10000 + Y*100 + Z)*100` + the commits after the tag, at most 99, so a later build always installs over an earlier one; minor and patch up to 99) and the commit (`-dirty` with uncommitted changes); `tool/build.sh <flutter build args>` passes them to `flutter build` (`--build-name`, `--build-number`) and to the app (`APP_VERSION`, `APP_BUILD`, `APP_COMMIT` dart-defines, `AppConfig.version`…), shown with the environment, backend (and its release, `/api/health`, `serverVersionProvider`) and platform under "À propos" (copy button, for bug reports). A plain `flutter run` / `flutter build` is a "development build" 0.0.0. Release: tag master `vX.Y.Z` and push the tag.

- **Environments** (`core/config.dart`, `AppConfig`): `prod` talks to `https://guillaumedamiens.com` only, `dev` to `http://localhost:8080` only (the backend of the development machine; Android devices and emulators through `adb reverse`); they never mix. The environment comes from `--dart-define=APP_ENV`, else on the web from the page's host (`app.guillaumedamiens.com` = prod), else from the Android flavor (`appFlavor`), else dev. Android flavors (`android/app/build.gradle`): `dev` = `com.guillaumedamiens.app.dev` "Guillaume Dev" (orange icon in `src/dev/res`, cleartext HTTP to localhost allowed by `src/dev/res/xml/network_security_config.xml`), `prod` = `com.guillaumedamiens.app` "Guillaume" (App Links in `src/prod/AndroidManifest.xml`); `default-flavor: dev` in `pubspec.yaml`, so a plain `flutter run` / `flutter build` is dev (it also reaches the Linux build folder name). iOS and macOS have the same flavors: Xcode schemes `dev` and `prod`, configurations `<Debug|Profile|Release>-<flavor>` (mapped in both Podfiles), the flavor's values in `ios/Flutter/Flavor-*.xcconfig` and `macos/Runner/Configs/Flavor-*.xcconfig` (project-level base configurations, so the widget extension reads them: `APP_BUNDLE_ID`, `APP_DISPLAY_NAME`, `APP_GROUP_ID`, `GOOGLE_REVERSED_CLIENT_ID`), the Runner's own per configuration (`ios/Flutter/<config>.xcconfig`, `macos/Runner/Configs/Runner-<config>.xcconfig`: CocoaPods' file of that configuration, then the flavor's). Team `L846MR2M2R`, automatic signing. The Xcode projects were edited with the `xcodeproj` Ruby gem; new targets, files or configurations go through Xcode or that gem, never by hand. Dev builds show a "DEV" banner and prefix the keys they store (`AppConfig.storagePrefix`: `LocalStore`, `TokenStore`, onboarding flag). `API_BASE_URL` / `WEB_APP_URL` still force the URLs.
- The home screen widget's class is addressed by its qualified name (`com.guillaumedamiens.app.NextDepartures`): the dev flavor's application id differs from the Kotlin package.
- The router keeps the requested page in `from` through the splash, welcome and sign-in pages, so deep links survive them; a signed-in user leaves the sign-in pages for `from` (`Routes.signIn(from)`).
- `--route` is ignored on Linux desktop; on the web the routes are real URLs (`/stops/IDFM:71264`, `/lines/C01743`).

## Architecture (`lib/`)

- `main.dart`: path URL strategy, `ProviderScope`. `app/`: `app.dart` (`MaterialApp.router`, locale from `localeProvider`, light/dark from the system; Material from the `material_ui` package, imported instead of `package:flutter/material.dart`, deprecated since Flutter 3.47, with `GlobalMaterialLocalizations.delegates` of `material_ui`; `MaterialUiCompatibilityBridge` gives the app's theme and localizations to flutter_map, vector_map_tiles and maplibre, which still build theirs from Flutter's own Material; the `flutter gen-l10n` output, which still lists flutter_localizations' delegates, is left out of the analysis), `theme.dart` (`AppTheme`), `routes.dart` (paths), `router.dart` (go_router: session redirect via `refreshListenable`, `ShellRoute` for the map pages; pages without transition, `NoTransitionPage`: the panel swaps them in place and the sheet's scroll controller drives the list of one page only), `shell.dart` (`AppShell`).
- **Layout**: `AppShell` puts the page in a side panel next to the map from 840 px wide, in a `DraggableScrollableSheet` over the map below. Pages use `PanelScrollScope.of(context)` as the controller of their main scroll view (null in the wide layout, and for pages not on top; `app/panel_scope.dart`, exported by `shell.dart`); the sheet can't move without that list attached, not even by its handle, so a page's loading and error states are lists too (`AsyncView(page: true)`). The sheet's sizes come from the page (`SheetProfile`, `sheetSizes` in `app/sheet_sizes.dart`): lowest height keeping the page's header above the system's navigation bar (`bottomInset`: out of the system's swipes; there the shell puts the page's list back at its top, `_topAtLowest`: its header shows, and a swipe on it raises the sheet, which a list left scrolled down would take and scroll instead), middle size (where it opens and snaps; GO fits it to what its card going on shows at rest with `PanelSheetScope.fitContent`, followed as it grows while the user hasn't moved the sheet; looking at another card doesn't move it), never under the status bar; search and traffic are locked at full height, a stop's page opens higher (0.62: its departures at once, the stop on the map above, like Citymapper). Like Citymapper, a new page opens at its middle size, going back finds the page below at the height it was left at, and the same page with other parameters (a journey's options, a line's direction) keeps the sheet where it is (`SheetHistory`). The shell moves the sheet with its own animation, a jump each frame, once the page's list is attached (`DraggableScrollableController.animateTo` stops as soon as a list leaves the sheet, which a page change does); the snap sizes stay the same list while unchanged (a new list has the sheet snap again, interrupting a drag). Pages are laid out at least 180 px high and clipped when the sheet is lower (no overflow). The status bar is over the map, which stays light: dark icons. Shortcuts: `/` search, `Esc` back.
- **Map** (`core/map/`): one `MainMap` behind every page, drawn by `MapLibreMainMap` on Android, iOS and the web (package `maplibre`: native SDKs, maplibre-gl-js on the web, loaded by `web/index.html` from unpkg, pinned, its files checked by the browser against their `integrity` hashes (`test/web_page_test.dart`), with a patch: the map resized with its container, `fitBounds` without the padding of the previous move; OpenFreeMap vector tiles, no key: Liberty, in dark mode too (Fiord, the dark style, showed too little), without its points of interest nor its stations (`core/map/base_map_style.dart`: `baseMapStyleUrl`, `hiddenStyleLayers`, removed once the style is loaded; streets, places and 3D buildings stay); what a page shows and the user dot are layers of the map itself (`MapLibreOverlay`, `core/map/maplibre_overlay.dart`), so they move with it (Flutter widgets over the map were placed once it had moved, a frame or more behind, trailing it as it panned): from the bottom the paths (`mapLibrePathLayers`: solid ones on a light casing, walks as round dots alone like Citymapper's, the map seen between them, `DotsLayer`: dashes of no length with round ends; flutter_map's dots without border; kept while unchanged, the ones after a change drawn again in order under the overlay's layers), the circle of accuracy, the pins turned with the map (`MapPin.rotation`: a vehicle's pointer, `VehiclePointer`, under its circle), the upright pins, the user's heading lying on the map, the user dot; each pin's look is drawn once from its widget into an image of the map (`StyleController.addImageFromWidget`, at the screen's density: the web is told so, Android and iOS take it for logical pixels, so `icon-size` is 1 / density there, `overlayIconSize`), named by `MapPin.image` (required with a `child`: `vehicle-C01371-24.0-late-false`, `callout-…`; a dot's from its color, icon and size) and the theme's brightness, shown once there (`pinsGeoJson`), taken off past 200 unused; GeoJSON sources updated only when their text changes; a tap asks the map which pin is under it (`tappedPin`, `featuresAtPoint`); with a screen reader on (`accessibleNavigation`), invisible labelled boxes in a `WidgetLayer` keep the pins named and tappable) and by `FlutterMainMap` elsewhere (desktop, and tests: `mapTilesEnabledProvider` false; flutter_map with the same OpenFreeMap style drawn in Dart by `vector_map_tiles`, a beta, the only versions for flutter_map 8: `baseMapStyleProvider` reads it once and drops the same `hiddenStyleLayers` (`withoutHiddenLayers`); flat, no tilt nor 3D buildings; the package `maplibre` has no Linux side, and on Windows and macOS only an experimental WebView); `useMapLibreProvider` chooses. Both read what to show with `watchMapView` and share `FollowHeading` and the widgets of `map_pins.dart` (`PinView`, `UserDot`, `RecenterButton`, `AccuracyCircle`). Like Google Maps, a soft blue disc around the user dot shows how sure the position is (the user is somewhere in it): the accuracy of the fix the dot comes from (`watchMapView`'s `accuracy`: GO's smoothed position carries its fix's, `PreciseUserPosition`; the regular one's is `userAccuracyProvider`), under the pins, not drawn within the dot's halo (`AccuracyCircle.radiusFor`, checked again as the camera zooms); on MapLibre a circle layer lying on the map (flattened when tilted) whose radius doubles at each zoom level from its radius at zoom 0 (`accuracyGeoJson`), on flutter_map a `CircleLayer` in meters. A page shows things on it by wrapping its content in `MapOverlayScope(overlay: MapOverlay(pins, paths, fit))`; overlays are keyed by route location, the map shows the current one (`routerLocationProvider`). The camera only moves when `fit` changes, and frames it in the part not hidden by the panel where it rests (`MapPanel`, `core/map/map_panel.dart`: the shell gives the sheet's height live and where it is going); as the sheet moves, what is in the middle of the part left above it stays in its middle at once, like Citymapper (followed once a frame, after the camera's own animation: MapLibre's padding changed without animation, its camera center being that of the padded area; flutter_map's center moved by half the sheet's move, `visibleCenterShift`), up to 70 % of the map hidden (`maxPanelShare`; higher, the sheet is the page and the camera stays put); the first fix centers the user there too, not behind the sheet's edge; with `follow` (`MapFollow`: GO on foot or by bike, `goFollow`, marked as the user's, `MapFollow.user`) it follows the user instead, in first person on foot and by bike: the user at 72 % of the visible height (`followPadding`), zoom 18, tilted 45° to see the way further ahead (`MapFollow.firstPersonPitch`, MapLibre only); in a vehicle (a car's step, or a move ridden faster than it goes: `GoVehicleSpeed`, over 4.5 m/s on foot or 9 m/s by bike two fixes in a row, back after fifteen slow ones, `GoState.inVehicle`) from overhead (`MapFollow.overhead`: north up, zoom 15, the user in the middle, no heading cone; also a vehicle followed from a line's page, not the user's: the camera on the vehicle, the dot and its circle staying on the user, GO's smoothed position included); on board a ride, the map frames what is left of it; until the user moves the map ("Recentrer" button, above the sheet): turned by the device's heading where it has a compass (`MapFollow.compass`, `core/location/device_heading.dart`: Android's rotation vector sensor through `DeviceHeading.kt` and the `com.guillaumedamiens.app/heading` event channel, iOS's Core Location compass through `DeviceHeading.swift` on the same channel (the top of the screen as the interface turns), the browser's `deviceorientationabsolute` events; only while following and while the app is on screen (`appShownProvider`, `core/platform/app_shown.dart`; stopped by `deviceHeadingProvider` itself, since an app off screen draws no frame and its widgets don't rebuild), about 16 headings a second (`SENSOR_DELAY_UI`), smoothed; `FollowHeading` passes them on at most every 50 ms, and only once 6° away from the heading shown unless the device is turning (1.5° from one heading to the next): a phone lying indoors wanders by 15°, and each turn has MapLibre draw for most of a second), else the way ahead up (`GoStep.headingFrom`: the path 30 m further than the user's projection on it); markers stay upright (the user dot turned by the heading less the map's bearing). GO asks the app's single position feed (`core/location/position_feed.dart`, `PositionFeed`: Geolocator keeps one stream on Android, a later request getting the first one's settings) for what the moment needs (`goLocationNeed`: a fix a second on foot or by bike on screen, every 2 s off screen, 5 s waiting, 3 s on board, nothing more once arrived; the feed opens again with the new settings) and starts from the last known position (`Geolocator.getLastKnownPosition`, else the app's regular one) so that the map follows at once; speeds count for what their accuracy leaves of them (`sureSpeed`: a phone lying indoors reports 2.5 ± 2.1 m/s); what the map shows (the dot, and the camera of the user's follow: `watchMapView` puts it there) is `preciseUserPositionProvider`, smoothed by `GoSmoother` (`features/go/go_smoother.dart`: a glide of 0.9 s to each fix, then on along the walking or cycling way at the measured speed, 12 m at most beyond the fix; standing still, a fix within its accuracy (3 to 25 m) of the dot is the GPS wandering and moves nothing), redrawn every 200 ms on foot and 100 ms by bike, only while it moves and the app is on screen; small steps of the camera (`MapFollow.closeTo`: the smoothed position, the compass) glide towards the last view asked (`MapFollow.glideTo`, step by step on a timer of `MapLibreMainMap` running only until it is there: every 16 ms while turning, 40 ms otherwise, `MapFollow.glideStepTo`; not a ticker, which would draw every frame of the screen, 120 a second here), bigger ones are animated. The fixes themselves drive `GoTracker`. Development builds show under GO's header how the fixes come (`goFixStatsProvider`: accuracy, mean time between fixes, age). Long press (right click on desktop) on the map: `features/map_place/map_place_sheet.dart` (`MainMap.onLongPress`, given by the shell), the point named after its address (`/api/v2/places/reverse`, "Point sur la carte" without one) with "Y aller", "Partir d'ici" and the departures around.
- **API** (`core/api/`): `models.dart` (freezed models of `/api/v2` and auth), `MobilityApi` (v2 endpoints), `AuthApi`, `api_providers.dart` (every request carries `X-App-Platform` and `X-App-Version`, `AppConfig.clientHeaders`: the backend counts the devices per platform and version, anonymously). `AuthInterceptor` (dio `QueuedInterceptor`) adds the access token: the account's, renewed with the refresh token (rotated on each use, so requests wait for a single refresh), else the device's guest token (`POST /api/auth/guest`, fetched when missing or rejected); a rejected refresh token is reported to `AuthController` and the request goes on as a guest. Errors become `ApiException` (message in the app's language, backend problem detail `code`; `signInHelps` for the guest limits `guest_journey_limit` / `guest_quota_exhausted`, where `ErrorMessage` offers to sign in).
- **Auth** (`features/auth/`): `AuthController` (`unknown` / `guest` / `signedIn`). Nothing requires an account: a guest uses the whole app with capped usage (backend: a share of the PRIM quotas, a few journeys a day), favorites and recent searches on the device only; signing in (account menu, sign-in button of a guest-limit error, last welcome page, "Continuer sans compte" back) keeps them and the favorites join the account; signing out (or a lost session) clears the account's device copies and goes back to guest. `TokenStore` keeps the account's access token in memory and its refresh token in `flutter_secure_storage`, plus the device's guest token (kept at sign-out, so its daily allowance follows the device); no password exists.
- **Google sign-in** (`features/auth/google/`, packages `google_sign_in` + `google_sign_in_web`): the app gets a Google ID token and `AuthController.signInWithGoogle` exchanges it at `POST /api/auth/google`. Android: `authenticate()` opens the system account chooser (Credential Manager), `serverClientId` = the web client (`AppConfig.googleWebClientId`, so the token's audience is the client the backend accepts); iOS and macOS: Google's page through the flavor's iOS OAuth client (`AppConfig.googleAppleClientId`, its reversed id as `GOOGLE_REVERSED_CLIENT_ID` in the flavor xcconfigs, the URL scheme of both Info.plists; macOS keychain group `com.google.GIDSignIn`), `serverClientId` the web client too; offered once those clients exist (empty for now: a placeholder scheme); Google recognises the app by package + SHA-1 through the Android OAuth clients of the project ("Guillaume Dev": `com.guillaumedamiens.app.dev` + debug key; prod: `com.guillaumedamiens.app` + upload key, and later the Play signing key). Web: Google's own button (`google_button_web.dart`, conditional import, in the app's language), results through `GoogleSignIn.authenticationEvents`; allowed origins `https://app.guillaumedamiens.com` and `http://localhost:5000` (run the dev web app on that port). Linux and Windows have no Google SDK (`googleSdkAvailable` is false there): the sign-in goes through the system browser and the backend (`browser_sign_in.dart`, `BrowserSignIn`; `LoopbackBrowserSignIn` in `browser_sign_in_io.dart`, behind a conditional import since it needs `dart:io`): the app listens on a free port of the loopback, `POST /api/auth/google/desktop { port }` gives Google's page, a `state` and a `verifier`, the page is opened with `xdg-open` (Windows: `rundll32 url.dll,FileProtocolHandler`; no `url_launcher`), the backend sends the browser back to `http://127.0.0.1:<port>/?code=…&state=…` where it gets a page saying to return to the app, and the code is exchanged with the verifier for the account's tokens (`AuthController.signInWithTokens`: no ID token on these platforms, and no OAuth client of their own, the backend uses the web client and its secret); the button shows that the browser is waited for, with a way to give up (10 min at most, like the backend). Not offered on iOS and macOS until their clients are set (`googleSignInAvailable`): the login page then says so and the app goes on as a guest. Sign-in is **Google only** (no password accounts). `googleAccountChooserProvider` opens the account chooser (Android; null on the web, on Linux and Windows, and where Google is unavailable; the tests replace it), `googleBrowserSignInProvider` is the sign-in through the browser (Linux, Windows; null elsewhere and in `pumpApp`, which never opens the machine's browser). Sign-out and account deletion also sign out of Google.
- **Account page** (`features/auth/account_screen.dart`, `/account`, account menu when signed in; also the web URL Google Play asks for to delete an account, a guest is offered to sign in back to it): email / first name (`/api/v2/me`), export (`/api/v2/me/export`, through `exportText`: browser download, Android share sheet, else clipboard), sign-out, deletion (`AuthController.deleteAccount`: `DELETE /api/v2/me`, then the device forgets the account and carries on as a guest); for admins, `ApiTokensSection` (personal API tokens for Bruno and scripts, `/api/v2/me/api-tokens`: create with a name, value shown once with a copy button, revoke). `/api/v2/me` and its export are never served from the offline cache.
- **Location** (`core/location/`): `userLocationProvider` (geolocator through the app's `PositionFeed`, a new position every 25 m whatever GO asks the feed, or a fix twice as sure as the one given (the accuracy circle shrinks as the GPS settles); how sure it is in `userAccuracyProvider`; the feed is closed while the app is off screen, unless GO follows a journey; null when unavailable, e.g. Linux without GeoClue; `locationIssueProvider` + `fixLocationIssue` offer to turn location on / allow it on phones, retried when the app resumes); `nearbyOriginProvider` falls back to the map center; `nowProvider` ticks every 15 s for "3 min" labels.

## Design

Citymapper-like, uncluttered: a light grey page (the sheet) with white rounded cards (`AppCard`, radius `AppTheme.radius`), near-black text, one green (`AppTheme.brand`, the color scheme's primary) for what acts or moves: real time, "Partez dans…", GO, the main action of a page (`RoundAction(primary: true)`, "Y aller"); line colors are the only other colors. State colors come from the `AppColors` theme extension (`context.colors`: `live`, `delayed`, `warning` (last metro, elevators, schedule only), `cancelled`, `card`, `muted`, `subtle`), never from `Colors.green`/`orange`. Inter has 400/500/600 only: titles are w600, nothing bolder. Pages start with a back button and a large title, then a row of round actions (stop page) or the essentials (line, journey: duration and GO), then titled sections of cards. The home page (design 2b): the kinds of departures chosen over the map (`NearbyMapFilters`, home page only: all, rail, bus, tram, Vélib; also filters the map pins; a chosen kind taps back to all), then in the panel the search pill, the suggestion (`suggestedPlace`: home in the evening, work in the morning, when saved and away from it) which, with a daily trip there (`tripTo`), is that trip's card (`DailyTripCard` with a `heading`, left out of "Mes trajets"), else a chip; saved places as pills (tap: `goToPlace`, the next departure of the trip saved there without a search; long press: change or delete), the traffic card, daily trips, favorite stops, favorite lines with their traffic (normal, disrupted with the first title), then the nearby departures (a long press saves a stop). A daily trip card: when to leave ("Dans 4 min", green), times and next departures, duration, GO, its lines, a disrupted line of the trip; within the hour before the last ride of the night, "Partez avant 00:33" replaces when to leave (and the duration). Dark mode mirrors it (`AppColors.dark`).

## Conventions

- State: Riverpod 3 providers written by hand (no riverpod_generator). Models: freezed + json_serializable.
- No `dart:io` / `Platform` outside platform-specific code: everything must run on the web and desktop.
- User-facing strings in `lib/l10n/app_fr.arb` (template) and `app_en.arb`, generated by gen-l10n into `lib/l10n/generated/` (not committed; `flutter pub get` or `flutter gen-l10n` rebuilds it). Widgets use `context.l10n`; code without a context (formatting helpers, `ApiException`, GO alerts and notification, home screen widget) uses `currentL10n`. Data from IDFM / Navitia (stop names, disruption messages, walking instructions) stays in French. Times from the API are UTC (`Departure.time`), display with `formatClock` / `departureLabel`.
- Stop areas (`IDFM:71264`) and IDFM line ids (`C01371`) everywhere, as in the backend v2 API.
- Accessibility: icon-only buttons get a `tooltip` (it is their screen reader label), tappable map pins a `label`. Layouts must hold with a large system text size (×1.8 checked): fixed row heights go through `MediaQuery.textScalerOf(context).scale(...)`, and crowded rows drop or move secondary items from ×1.3 (departure times, traffic badges, the stop's "Y aller" label, the journey toolbar).
- Main actions give a light haptic (GO, choosing a departure, favorites). Tests come with every change (see Tests), and the app is still checked by running it.

## Tests

- `test/support/`: `FakeBackend` (dio `HttpClientAdapter`: answers per method and path, `*` for a segment, `down` for no network, records the requests as sent), `MemoryStore` (`LocalStore` in memory), `samples.dart` (models as the backend sends them: Châtelet, Gare de Lyon, Nation, métro 1, RER A, bus 38, like the backend's integration tests), `testContainer` (providers on a fake backend; signed in when a refresh token is given), `pumpApp` (the whole `MobilityApp`, phone size, French, map tiles off, position at Châtelet, onboarding flag in memory; `settle` pumps for a while since the app keeps periodic timers; `closeApp` at the end of each test), `standardBackend()` (usual answers around Châtelet, times relative to now).
- `test/core`, `test/features`: logic (formats, geometry, models' JSON, errors, token renewal, offline cache, journey retiming, GO tracker, vehicles, session, favorites, recent searches). Code without context formats with `currentL10n`: tests set it with `useLocale` (and `initializeDateFormatting()` for dates).
- `test/flows`: the app tapped through like a user (home → stop → line → favorite, search, traffic, offline notice, language, journey and detail, guest limit, sign-in/out, account, welcome pages). Find widgets by text through `currentL10n`, by tooltip, or by type (`LineBadge`, `JourneyCard`); `visibleTexts(tester)` lists what is on screen when a test fails.
- `integration_test/`: the same harness on the real engine (`app_test.dart`, Linux desktop), and `device_heading_test.dart` (the compass of a real phone, skipped elsewhere). One file per `flutter test` run: started a second time in the same run, the Linux app never connects (the CI loops over the files).
- Seams for the tests: `dioFactoryProvider` (backend clients), `localStoreProvider`, `onboardingDoneProvider`, `localeProvider`, `userLocationProvider`, `mapTilesEnabledProvider`, `deviceHeadingProvider` (no compass in `pumpApp`), `positionFeedProvider` (a `PositionFeed` whose `open` gives the tests' streams and records their settings), `googleAccountChooserProvider` (`pumpApp` signs in with a test ID token; pass `googleAccountChooser: null` for a device without Google), `googleBrowserSignInProvider` (`googleBrowserSignIn:` a fake `BrowserSignIn` for Linux and Windows; the real one is tested on a real port in `test/features/auth/browser_sign_in_test.dart`, the test playing the browser); plugins without a test implementation (secure storage: `FlutterSecureStorage.setMockInitialValues`) or guarded (home widget, Google sign-in on desktop).

## CI (GitHub Actions)

- Nothing builds iOS and macOS in the CI: the Swift side and the Xcode projects (`ios/`, `macos/`) are only checked by building on a Mac.
- `.github/workflows/build.yml`, every pull request and push to master, two checks required to merge (branch protection): "Test" (`pub get`, `build_runner`, `flutter analyze`, `flutter test`, integration tests on the Linux app under `xvfb-run`) and "Build" (production builds through `tool/build.sh`, on the whole git history for the version: web with `--no-web-resources-cdn`, Android APK `--flavor prod`, APK kept 14 days as an artifact). Flutter pinned to the local version (3.50.0): update both together. Flutter 3.50.0's Linux engine draws the app half a window down and left where it can't use `glBlitFramebuffer` (NVIDIA: [flutter#195885](https://github.com/flutter/flutter/issues/195885), fixed for 3.50.1); `linux/flutter_3_50_0_fix.cmake` corrects the bundle's copy of exactly that engine at install (its compositing shader, same length, checked by SHA-256 before and after; any other engine left alone): remove it with 3.50.1. The CI's integration tests (Mesa under `xvfb-run`, which blits) never show that bug.
- `.github/workflows/deploy-web.yml`, tag `v*` (or by hand on a tag; a commit of master only; the workflows' actions are pinned to commits, updated by Dependabot, `.github/dependabot.yml`): checks that the tag is the version (`vX.Y.Z` on the commit, `tool/version.sh`), builds the production web app with `tool/build.sh`, publishes the archive in the tag's GitHub release, and the VPS downloads it as the `deploy` user (uploads from GitHub's runners to the VPS crawl at ~20 KB/s) and checks its SHA-256 (secrets `DEPLOY_HOST`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, the same as website-back's): `/var/www/guillaumedamiens-app/releases/web-<tag>-<sha>`, then the `current` link nginx serves is switched atomically; the 5 latest releases stay (roll back by pointing `current` to an older one).
- `.github/workflows/release.yml`, tag `v*` too (same checks on the tag; the release is created by whichever of the two workflows comes first): the production apps as assets of the tag's GitHub release, one job each. Android: APK signed with the release key from the secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, not published without them (a runner's debug key changes at every run). Linux `tar.gz`, Windows `zip` (with the Visual C++ runtime DLLs; `APP_ENV=prod`, no flavor). Nothing for iOS and macOS (no Apple Developer Program: nothing others could install). A pull request that changes the workflow runs it dry (artifacts of the run, nothing published): the way to test it. User instructions: README, "Installer une release".
